# Notes implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Add durable repository notes, clear dashboard and task views, and local MCP tools.

**Architecture:** One project-pinned notes service owns notes.json and publishes full snapshots through the existing SSE broadcaster. React shares one notes collection and reuses the editor and cards in dashboard and task views. A stdio MCP server calls the same loopback API.

**Tech stack:** TypeScript, React 19, Fastify 5, Zod 4, Vitest, official MCP TypeScript server SDK, Windows-compatible project lease.

**Spec:** `docs/superpowers/specs/2026-10-06-notes-design.md`, approved by the user on 2026-10-06.

## Global constraints

- Notes belong to one repository. All notes includes general and task notes from that repository.
- Omitted or null taskIssue means General; each task link is a GitHub issue number.
- Body is required; preserve whitespace; title limit 240 characters; body limit 64 KiB in UTF-8.
- Settled notes remain below active notes in a collapsed section and can be reopened.
- Notes survive task removal, completion, and worktree cleanup.
- Keep runtime data and client configuration outside managed project checkouts.
- Persist before broadcasting; notes mutations never call GitHub reconciliation.
- No direct-file MCP fallback. Mission Control's server must be running.
- Preserve the existing user changes. Work in an isolated copy of the current workspace and integrate only the notes delta.

## Review focus

1. A creation retry after task removal must return the original note without current-membership validation.
2. A delayed pre-reconnect response must not overwrite the new notes session or an updated note.
3. A new-note draft must keep its creation request ID through reload and an uncertain save.
4. An unavailable or corrupt store must preserve data and leave the task board usable.
5. A forgotten task must remain selectable as a notes filter without becoming a valid new task association.

## Execution and interface map

Task 1 owns the notes contracts, store, lease, routes, and startup integration.
Task 2 owns frontend model/state/components, API integration, and UI styles.
Task 3 owns MCP, CLI registration, dependencies needed by MCP, and setup docs.
Run implementation tasks sequentially and review each before the next. The controller owns isolated-workspace setup, dependency coordination, browser verification, and final integration. No worker edits another task's owned files without coordination.

Public contracts in `src/shared/notes.ts`:

```ts
type NoteStatus = 'active' | 'settled';
interface Note {
  id: string; title: string | null; body: string;
  taskIssue: number | null; taskTitleAtLink: string | null;
  status: NoteStatus; createdAt: string; updatedAt: string;
  settledAt: string | null; revision: number; clientRequestId: string;
}
interface NotesSnapshot {
  projectId: string; serverSessionId: string; revision: number; notes: Note[];
}
interface NoteResult {
  projectId: string; serverSessionId: string; note: Note;
}
interface NoteTask { issue: number; title: string }
interface NotesStatus {
  projectId: string; serverSessionId: string; available: boolean;
  code?: string; error?: string;
}
```

Routes return NotesSnapshot, NoteResult, or `{ projectId, tasks: NoteTask[] }`.
PATCH success includes serverSessionId. Errors return `{ code, error, currentNote? }`.
Export `MAX_NOTE_BODY_BYTES = 65536`, `MAX_NOTE_TITLE_LENGTH = 240` and shared Zod creation/update schemas. The browser never imports Node APIs from shared modules.
